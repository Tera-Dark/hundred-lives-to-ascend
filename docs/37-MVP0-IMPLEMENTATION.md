# 37 · MVP-0 可玩交互原型交付与验证记录

> **本文件是已实现代码范围的交付说明，不是未来全量 PRD。** 主体在 [../prototype](../prototype/README.md)。已在本地以 Node.js 执行逻辑测试（**10/10 通过**），并以无网络 Playwright 浏览器进行了页面加载、选玄修与推进至药庐事件的交互冒烟测试，未发现脚本异常。其余内容未经过真人试玩，不宣称整体平衡已完成。

## 一、代码架构与技术取舍

- `prototype/game.mjs`：不依赖 DOM 的可序列化生命周期状态机。普通一年只增长一次世界历、角色年龄、修为、灵石；事件可暂停自动跳年。
- `prototype/app.mjs`：竖屏四入口的点击渲染/按钮绑定，使用 `localStorage` 保存 V1 原型存档；不能当作具备迁移方案的正式存档系统。
- `prototype/index.html` + `prototype/style.css`：无构建、无外部 UI 依赖的轻量墨绿金色验证界面。
- `prototype/tests/game.test.mjs`：Node 内置 test runner 逻辑回归，无需安装依赖。

**为什么不是 Cocos 3.8.8 工程：** 本阶段优先验证关键选择是否有意义而非投入编辑器场景、美术、TapTap 适配与商业SDK。将来如果交互通过，再将独立规则移植为 TypeScript 域层，UI 以 Cocos Creator 2D 竖屏实现。当前原型的浏览器栈**不变更最终Cocos路线**。

## 四、已知风险及接下来要玩家验证的内容

1. **这还是验证工具，不是完整游戏**：年数目前有即时跳转按钮，没有正式 7–10 分钟的时间速率、剧情音效与美术；玩家长寿后的主动内容很有限。
2. **数值没有冻结**：闭关18石+2年、丹方3分支与RP+25%是候选参数；所有公式可追溯但未对随机事件/双槽遗物做全量平衡。
3. **两世之间的新鲜度**：世界60不会重演，但后世事件仍重复使用较少模板；必须观察第二世是否足够有追求。
4. **遗物系统只是极浅验证**：4个功能图谱、2装备槽；白至彩76件、10级碎片、兑换、4个追加携带位未实现。
5. **世界95事件并不等于已完成世界160后续篇章**：世界160只安全暂停。
6. **正式架构欠缺**：当前 `game.mjs` 的内部 JS 数据需进一步 TypeScript 类型化、严格防存档篡改、数值版本迁移、解耦配置、测试覆盖率，之后才能投入 Cocos 工程。

## 五、反馈建议（目标是游戏性，而不是写更多设定）

请分别玩两次：一次玄修靠筑基，一次丹修靠护脉丹。每次只留意：
- 能否很快看出**当前最重要的资源瓶颈**？
- 面对心魔与荒谷时，是否曾改变原来的修行计划？
- 玄修闭关是否有“投入有利/投入亏”的清晰判断？丹修三丹方是否真想选择不同一张？
- 死亡→轮回后，永久成长和旧玉线索是否足以让你**想主动继续第二世**？
- 有没有“我只是在按快进等年数”而不是进行有意思的决策？

**阶段结论：MVP-0 可运行且核心状态约束初步通过；真正的游戏乐趣、完整生命周期与 TapTap 适配均未验收。**
